# Projects Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Projects tab: server-side projects (one future video each), created from a template or a preset, edited in the existing compose editor with autosave, rendered one by one or in bulk.

**Architecture:** A `project` table + `/projects` API in NestJS (renders go through the existing `RendersService.create`, linked by `render_job.project_id`). In the admin the compose screen gets a second draft source: the same `ComposeDraftState` interface, backed by the API instead of the browser store. The projects table reuses the Renders pieces (day groups, checkboxes, selection bar).

**Tech Stack:** NestJS + TypeORM (Postgres), zod 4 (`@vgen/shared`), Vue 3 + Vue Query + Pinia + reka-ui / shadcn-vue.

**Spec:** docs/superpowers/specs/2026-11-22-projects-design.md

## Global Constraints

- The quick flow (Templates → `/compose/:templateId`) keeps its browser draft and behaviour; after Render it still goes to Renders.
- Admin layers: lib → api → queries → stores → composables → components → views (`apps/admin/eslint.layers.js`); thin views.
- English code, comments and UI copy; pnpm only; everything through `make`.
- `make lint`, `make test` pass after every task; `make admin-check` after admin tasks, including the unchanged `/compose/<id>`.
- No engine / template code changes (renders of existing templates stay identical).
- Commits only when the owner asks.

## Review Focus

- A project opened after its template's version changed: settings are sanitized (reset fields reported) and saved back, never a broken screen.
- Leaving the project editor within the save debounce: the pending save is flushed, nothing is lost.
- Bulk render with one project missing a photo: the others are queued, the bad one is listed with the reason.
- A photo used only by a project: "Clean up unused" keeps it; the Media page shows the project usage.
- Two tabs on the same project: last write wins, no crash (single user; documented, not solved).

### Task 1: Shared contract

**Files:** create `packages/shared/src/api/projects.ts` (+ export in `api/index.ts`, test `projects.test.ts`); modify `packages/shared/src/api/renders.ts`, `packages/shared/src/api/media.ts`.

**Produces:**

- `ProjectDraftSchema` = `{ settings: record, media: record<string, string | string[] | null>, quality, scale, presetId: uuid|null }` (what the browser draft holds).
- `ProjectDtoSchema` = draft + `{ id, name, templateId, templateVersion, thumbnail: RenderFileDto|null, lastRender: { id, status, progress, createdAt, finishedAt, error } | null, createdAt, updatedAt }`.
- `ProjectScopeSchema` `{ templateId?, rendered?: 'yes'|'no' }`; `ProjectListQuerySchema` = page + scope; `ProjectDaysQuerySchema` / `ProjectSelectableQuerySchema` (scope + `tz` + `day?`, reuse `TimeZoneSchema`, `DayKeySchema`); `ProjectDayDtoSchema` `{ date, total, notRendered }`.
- `CreateProjectRequestSchema`: `{ templateId?, presetId?, name? (1..256), settings?, media?, quality?, scale? }` with a refine "templateId or presetId".
- `UpdateProjectRequestSchema`: partial `{ name, settings, media, quality, scale, presetId }`.
- `ProjectIdsRequestSchema` `{ ids: uuid[] 1..500 }`; `RenderProjectsResponseSchema` `{ queued: { projectId, render: RenderJobDto }[], failed: { projectId, message }[] }`.
- `CreateRenderRequestSchema` and `RenderJobDtoSchema` gain `projectId: uuid | null` (default null).
- `MediaLibraryItemDto` gains `projectCount: int`.

### Task 3: API — projects module

**Files:** create `apps/api/src/projects/{projects.module,controller,service,repository,mapper}.ts`, `projects.service.test.ts`; register in `app.module.ts`; modify `renders.service.ts` / `renders.repository.ts` / `renders.mapper.ts` (accept and map `projectId`), `presets.service.ts` (export `findDefault(templateId)` if missing).

**Consumes:** Task 1 schemas, Task 2 entities, `RendersService.create`, `PresetsService`, `CatalogService`, `applyPreset`, `resolveTemplateDefaults`.

**Produces (service):** `create(request)`, `get(id)`, `list(query)`, `days(query)`, `selectable(query)`, `update(id, patch)`, `remove(id)`, `removeMany(ids)`, `render(ids): RenderProjectsResponse`.

- create: template from `templateId` or the preset's template; settings = `applyPreset(template, preset.props, request.settings ?? {})` when a preset is given (or the template's default preset when only a template is given), else defaults ⟵ `request.settings`; `media` from the request (sanitized with `sanitizeMediaRefs`), `name` default = preset name ?? template name.
- list / days / selectable: same scope + day SQL pattern as renders (`to_char(created_at AT TIME ZONE :tz, 'YYYY-MM-DD')`); `rendered=no` = no render_job with this project_id. Last render via a lateral join or a second query (newest `render_job` per project).
- thumbnail: first media id in slot order that is an image, else a video's poster (`MediaService.findMany` + poster variant URL).
- render: for each id, `RendersService.create({ templateId, props: {...settings, media}, quality, scale, presetId, projectId })`; `AppError` → `failed[]` with its message; other errors rethrow.
- Controller routes `days`, `selectable`, `render`, `delete` declared before `:id`.
- [ ] Service tests: create from template applies the default preset; create from preset keeps request settings on top; render with one invalid project → 1 queued, 1 failed; update bumps `updatedAt` and keeps `templateVersion` current.
- [ ] Probe with curl on the running stack (create, patch, render), then delete the test projects.
